# Этап 6. Решение о роли графа и кода

Сначала прочитать `00-common.md`. Начинать после этапа 3.

## Цель
Чётко зафиксировать, что решает граф, а что код, чтобы система не стала «JavaScript, нарисованным квадратиками».

## Контекст
Сейчас вся логика узла — JS в Script; граф выражает последовательность, ветвление и данные. С появлением циклов и потоков управления граф начинает дублировать язык программирования.

## Проектное решение (рекомендация; принять или изменить решением пользователя)
1. **Граф — оркестрация:** порядок шагов, параллелизм, ожидания, одобрения, ошибки и повторы, видимость для человека.
2. **Код — вычисления внутри шага:** разбор данных, преобразования, подготовка prompt. Если логика не нужна человеку на схеме, она остаётся в Script.
3. **Правило размера:** Script > ~80 строк или больше одного логического шага — повод разрезать; цепочка узлов, просто преобразующая данные без побочных эффектов, — повод свернуть в один Script. Рекомендация и предупреждение линтера, не запрет.
4. **Не плодить условные и арифметические узлы** без нужды (`If`, `Compare`, `Math` — только если без них что-то нельзя выразить, например ветвление по сигналам). Базовый набор потоков уже есть: `For`, `For each`, `While`, `Break`, `Continue`.
5. **Агентский цикл** — один хорошо протестированный библиотечный узел (`Tool-use loop`), а не сборка из квадратиков каждый раз.
6. **Критерий пересмотра:** если большинство реальных графов контроллера превращаются в один большой Script, ценность графа в другом (наблюдаемость, права, воспроизведение) — усиливать это, а не ветвление.

## Пошаговые задачи
1. Написать `docs/graph-vs-code.md`: правила и примеры «хорошо/плохо».
2. Линтер графа (предупреждения): слишком длинный Script; Script без объявленных прав (этап 4); цикл без ограничения/бюджета.
3. Через полгода использования собрать статистику (длина скриптов, доля узлов Library против сырых Script) и пересмотреть.

## Критерии приёмки
Документ принят пользователем; линтер встроен; в `examples/` есть эталонные образцы обоих стилей.
