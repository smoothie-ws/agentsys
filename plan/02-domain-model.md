# Этап 2. Модель состояния проекта (domain model)

Сначала прочитать `00-common.md`. Можно вести параллельно с этапом 1 после выбора терминологии.

## Цель
У контроллера есть явное, типизированное, постоянное представление «что за проект ведётся»: цели, задачи, решения, артефакты, история, ограничения. Сейчас «проект» в коде значит «рабочее пространство с графом», это другое.

## Что есть сейчас
- Слово «project» занято: `projects/{project_id}/...` — рабочее пространство редактора с workflow.
- Нет места для данных управляемого проекта; скрипты могли бы писать куда угодно через `agentsys(...)`.

## Проектное решение
1. **Терминология.** Управляемый проект назвать **Initiative** (или `Mission`; выбрать одно и записать). Редакторное «проект» не переименовывать массово.
2. **Ядро модели** — маленькое и обобщённое, не под конкретную предметную область:
   - `Initiative {id, title, goal, status, constraints, budget_id, created_at}`
   - `Task {id, initiative_id, parent_id?, title, description, status(todo|doing|blocked|done|cancelled), assignee(kind: node|human|agent, ref), depends_on[], due?, result_ref?}`
   - `Decision {id, initiative_id, summary, rationale, made_by, at, supersedes?}` — неизменяемый журнал, только добавление.
   - `Artifact {id, initiative_id, kind, title, uri|content_ref, version}`
   - `Note/Fact {id, initiative_id, text, source, confidence, at}` — долговременная память контроллера.
3. **Хранилище.** Отдельное пространство ключей в DB (`initiatives/<id>/tasks/<id>` и т.д.); изменения — append-only журнал (`initiatives/<id>/log`); состояние — проекция журнала. Без внешней БД на этом этапе.
4. **API.** Маршруты `initiatives/*` в новом `js/backend/routes-initiatives.js` в стиле существующих `route(...)`. Из скриптов — через `agentsys(...)`, с правами (этап 4).
5. **Транзакционность.** Изменения через `exclusive` + проверка версии (оптимистичная блокировка: `version` в теле), чтобы параллельные волны не затирали друг друга.
6. **Узлы Библиотеки** (скриптовые, поверх API): `Create task`, `Update task`, `List tasks`, `Record decision`, `Remember`, `Recall`. В движке никакой логики про задачи.
7. **Запросы.** Простые фильтры по статусу/исполнителю/зависимостям; без собственного языка запросов.

## Пошаговые задачи
1. Зафиксировать терминологию в `engine-design.md` (раздел «Словарь»).
2. Схемы данных (проверочные функции в стиле `bad()`/`isObject` из `db.js`), валидация на входе.
3. Слой `js/model/initiative.js` — чистые функции: применить событие → состояние, проверить переходы статусов, найти разблокированные задачи.
4. Маршруты, журнал событий, оптимистичная блокировка.
5. Узлы Библиотеки и пример графа «Planner → Task runner».
6. UI: страница Initiatives (список, дерево задач, журнал решений) — минимум для чтения; редактирование через те же узлы/API.

## Тесты
Переходы статусов; зависимости (задача не стартует, пока не готовы `depends_on`); конфликты версий; восстановление состояния из журнала; параллельные записи из двух волн.

## Документация
Новый `docs/initiatives.md`; обновить `docs/interface.md`, `README.md`.

## Риски
Раздувание модели. Правило: добавлять поля только когда есть узел, который их использует.

## Критерии приёмки
Граф может создать инициативу, разбить на задачи, вести статусы и решения; всё переживает перезапуск; конкурентные записи не теряются.
