## 0. Цель и границы

### 0.1. Цель

За 12 часов провести максимально полную, но безопасную работу по шести направлениям:

1. **Сократить объём кода** — удалить мёртвый код, дублирование и лишние слои, не сокращая функциональность.
2. **Увеличить производительность** — движок графа, сериализация состояния, отрисовка холста, серверные обходы.
3. **Повысить надёжность и автономность движка** — жизненный цикл рантаймов, восстановление после сбоев, сохранность данных, отсутствие утечек.
4. **Найти и исправить ошибки** — подтверждённые тестом, а не «на глаз».
5. **Убрать оверинжиниринг** — упростить механизмы, которые не окупают свою сложность.
6. **Составить список идей** на удаление, изменение и добавление функционала — **без реализации** в эти 12 часов.

### 0.2. Жёсткие ограничения

- **UI не меняется концептуально.** Нельзя переставлять панели, менять навигацию, названия разделов, набор кнопок, горячие клавиши, визуальный язык. Разрешено исправлять явные дефекты: сломанный фокус, неверный статус, обрезанный текст, недоступную кнопку.
- **Функционал не меняется концептуально.** Никаких новых страниц, API-маршрутов, полей графа, операций Script API, форматов хранения. Существующие маршруты, тела запросов, ответы и `openapi.json` сохраняют совместимость.
- **Формат `agentsys.text/1` не меняется.** Старые данные должны читаться без миграций.
- **Script API (`node`, `agentsys`, `context`) не меняется.** Семантика сигналов, `await emit`, `context.state`, Pause/Stop сохраняется.
- **Plugin API и поведение плагинов не меняются.**
- **Никаких новых зависимостей.** Только Node.js built-in и браузерные API. Dev-инструменты — тоже без npm-пакетов.
- **Никакой массовой переформатировки** файлов, которые не меняются по существу. Это создаёт шум в diff и мешает откату.
- **Один коммит — одна причина.** Если изменение не проходит тесты или превышает таймбокс на 50%, оно откатывается и попадает в идеи/отчёт.

### 0.3. Что не делаем

- Не добавляем страницы, панели, кнопки, поля, маршруты API, типы графа, операции Script API.
- Не переименовываем и не переставляем элементы UI; не меняем тему, сетку, шрифты, иконки.
- Не меняем формат `agentsys.text/1`, расположение файлов и ключи хранилища.
- Не добавляем npm-зависимости и сборку.
- Не переписываем тесты «под новое поведение»; сначала поведение, потом тест.
- Не удаляем пользовательские данные в `data/` без явного подтверждения.
- Не правим `js/backend/builtin-nodes.js` руками (он генерируется).
- Не реализуем идеи из `docs/ideas.md` и раздела 8 этого плана.

### 0.4. Определение готовности (DoD)

Работа считается выполненной, если одновременно:

- `npm test` зелёный, число тестов не меньше 230, добавлены регрессионные тесты на каждый исправленный дефект.

- Нет новых `unhandledRejection`, незакрытых воркеров и таймеров после Stop/закрытия сервера.
- Публичный контракт не расширен и не сужен: набор маршрутов, формы тел и ответов, страницы и горячие клавиши прежние.

- Создан `docs/ideas.md` — не менее 30 идей с приоритетом, риском и оценкой, **не реализованных**.

## 3. Правила работы

### 3.1. Ветки и коммиты

1. В рабочем дереве уже есть незакоммиченные изменения (33 файла, ~400 строк) **и несколько untracked-файлов текущей работы** (`js/app/extensions.js`, `js/pages/ext.js`, `data/plugins/hello-ui/`). **Не терять их.**
2. Создать ветку `hardening/12h` **от текущего HEAD, не трогая `main`**, перенести в неё рабочее дерево.
3. Сделать safety-коммит текущего состояния уже в ветке: `chore: checkpoint before 12h hardening`. **Не коммитить `.openchamber/`** — это артефакты сессии, а не код приложения; при сомнении перечислить файлы в `REPORT.md`.
4. Дальше — мелкие коммиты: `fix(engine): ...`, `perf(runtime): ...`, `refactor(model): ...`, `test: ...`, `docs: ...`.
5. В конце — либо fast-forward в `main`, либо оставить ветку и описать в `REPORT.md`, почему.

### 3.2. Таймбоксы и стоп-правила

- Каждая задача — **15–45 минут**. Дольше — дробить.
- Если дефект не воспроизводится за 15 минут — записать в `docs/ideas.md` / `REPORT.md` и идти дальше.
- Если после изменения `npm test` красный дольше 20 минут — откатить задачу, зафиксировать вывод, продолжить.
- Если сокращение кода требует изменения поведения — **не делать**; перенести в идеи.
- После каждого блока — зелёный `npm test`, обновление чекбоксов в этом файле, короткая запись в `REPORT.md`.

### 3.3. Приоритеты

- **P0** — потеря данных, зависание, утечка, падение движка, нарушение изоляции.
- **P1** — подтверждённый дефект, заметная деградация производительности, крупное дублирование.
- **P2** — чистота кода, CSS, документация, косметика.
- **P3** — только идеи, без реализации.

### 3.4. Протокол измерений

- Любая оптимизация: замер **до** и **после** на одном и том же сценарии, запись в `REPORT.md`.
- Никаких «стало быстрее» без числа. Если замер невозможен (браузер), — фиксируется причина и статическая оценка.
- Для тестов производительности использовать `tools/bench.js`, а не тайминги внутри `npm test` (тесты не должны зависеть от скорости машины).

## 6. Чек-лист поиска дефектов

Проходить по нему в B1/B6, не выдумывая новые фичи.

### Движок

- [ ] Run без `on_run` → понятное поведение, без ошибок.
- [ ] Повторный Run во время работы.
- [ ] Stop во время `sleep`, сетевого запроса, ожидания ветки.
- [ ] Pause/Resume: новые старты, продолжения после `await`, таймеры.
- [ ] Живое редактирование: удаление узла, смена кода, переподключение входа.
- [ ] `node.reread`, `node.flow.break/continue/cancel/abort`, `failFast`.
- [ ] Циклы данных и сигналов; цикл интерфейсов/групп.
- [ ] Ошибка в одной ветке не ломает соседние (если не `failFast`).
- [ ] Автоматический `out` + ручной `emit` + `return`.
- [ ] `context.state`: вложенные объекты, массивы, `undefined`, `__proto__`, конкурентные скрипты.
- [ ] Outputs: объект, `null`, число, строка, `undefined`, удаление.
- [ ] `node.display`: текст, JSON, base64-изображение, неверный base64.
- [ ] Custom Node: свободные входы/выходы, несколько экземпляров, `on_read` кэш.
- [ ] Удаление узла во время его выполнения; поздние записи отклоняются.
- [ ] Перезапуск сервера: state/outputs/displays на месте, стеков нет.

### Рантайм и хранение

- [ ] Эвикция не теряет данные и не вытесняет paused/working.
- [ ] Сбой записи → `storage_error`, повтор, отсутствие потери.
- [ ] `wait:true` дожидается сохранения.
- [ ] Shutdown сохраняет всё.
- [ ] Битый `.transaction.json`, частичная запись, повторный старт.
- [ ] Параллельные коммиты из двух клиентов/процессов.
- [ ] SSE: отключение, переподключение, отсутствие утечки `res`.

### API и безопасность

- [ ] `X-AgentSys`, Bearer, Host header, loopback/non-loopback.
- [ ] Path traversal в ключах и статике, `%2e%2e`, Windows-регистр.
- [ ] Огромное тело, битый JSON, не-объект, `null`.
- [ ] Неизвестные поля, прототипные ключи, дубли id, висячие порты.
- [ ] `if_cursor`/`If-Match`, конфликт 409.
- [ ] Права: project policy, grants, вложенные Custom Nodes, `secrets`.
- [ ] Плагины: маршруты, отключение, ошибки, клиентские расширения.

### UI (только дефекты)

- [ ] Фокус с клавиатуры на карточках, в диалогах, в инспекторе.
- [ ] `aria-label` у иконочных кнопок.
- [ ] Статус выполнения не врёт (Ready после ошибки — дефект).
- [ ] Панель не перекрывает выбранный узел при открытии.
- [ ] Мобильная навигация: закрытие, возврат, скролл.
- [ ] Пустые состояния и ошибки загрузки.
- [ ] Нет jank при перетаскивании 100+ узлов.

## 7. Риски и откат

| Риск | Вероятность | Влияние | Мера |
|---|---|---|---|
| Оптимизация меняет семантику сигналов | Средняя | Высокое | Коалесинг только уведомлений/записи; `latest` обновляется синхронно; тесты `wait/stop/pause` |
| Эвикция теряет состояние | Низкая | Высокое | Эвикция только после сохранения; тест на восстановление |
| Сокращение CSS ломает вид | Средняя | Среднее | Только дубли/мёртвые правила; ручной smoke; откат блока |
| Дедупликация резолвера расходится с валидатором | Средняя | Среднее | Сначала тесты на текущие сообщения; при расхождении — откат |
| Утечка времени на один дефект | Высокая | Среднее | Правило 15/45 минут, перенос в идеи |
| Грязное дерево пользователя | Высокая | Высокое | Safety-коммит до любых изменений |
| `data/` содержит пользовательские данные | Средняя | Высокое | Удалять только сгенерированные артефакты; при сомнении — не удалять |

**Точки отката:** safety-коммит, конец B1, конец B3, конец B4, конец B6. Откат — `git revert` конкретного коммита, не `reset --hard`.
