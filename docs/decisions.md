# Design decisions

1. A workflow is a live graph with one runtime and persistent JSON values. Run sends ordinary signals to enabled `on_run` Events.
2. Nodes are interpreted as reached. Graph edits update subsequent invocations, input rereads and emissions. An invocation already executing keeps its current function.
3. Script and Event are the behavior primitives. Library graphs compose them into Custom Nodes, branches, loops, delays and previews.
4. Signals control work; data wires provide JSON values. Fan-out is concurrent, an awaited emission joins its branches, and a signal call owns the work it started.
5. Script has signal input `in`, code input `script` and completion output `out`. Success emits `out`. Named signal outputs use `node.output.name.emit(options?)`; names are exact.
6. `context.state` is shared durable JSON. Run, Pause, Stop, navigation and restart preserve it, and so do port values and previews. JavaScript globals are host-local memory.
7. Pause gates code starts and continuations. Stop interrupts host work and keeps data. A restart restores data without resuming JavaScript stacks or external effects.
8. Execution has no depth, concurrency, time or result-size quotas. Valid structure, JSON data and permission checks always apply. Stop ends runaway code.
9. Each workflow's JavaScript host is isolated. Script calls are checked against the enclosing instances' grants and the project policy. Library defaults only initialize new instances. Code written through the API is quarantined.
10. Import/export and duplication carry graph JSON state and values. Undo covers definitions, not runtime state or external effects.
11. Inline Custom Node compositions without a Library source belong to their workflow and can be expanded, collapsed and edited through the checked graph API. Linked Library instances are edited in the Library.
12. Graph self-modification is a general capability (the checked API and the Graph nodes), not a feature of any one algorithm. The core contains no domain schemas, schedulers or controllers.
13. The server and the client are separate programs. The server has a fixed, documented feature set and does not load plugins; the client is static and reaches the server only through one versioned API transport. Closing a client cannot stop a workflow.
14. Client extensions are sandboxed packages installed in the browser. They run in an opaque-origin iframe with a narrow RPC API, cannot read the page DOM, browser storage, cookies or server token, and interact with the server only through the documented API. Page/card HTML is sanitized. This isolates code, not intent: installing a plugin is an act of trust.
15. A client plugin may create ordinary server resources (Library nodes, workflows, generic collection records). The server owns those resources, and execution never depends on the plugin or the client being present. This replaces server plugins that added privileged routes.
16. The server runs graphs; the client may keep the editing model for local validation, but never loads the interpreter (`executor.js`) or the backend routes. There is no browser-only backend mode.
17. UI preferences belong to the client (`localStorage`). Tokens are per tab (`sessionStorage`) and exchanged for HttpOnly sessions; project data, runtime and secrets belong to the server.
18. Idle workflow runtimes are released after ten minutes without a signal, and at most sixteen idle runtimes stay live (least recently used first). Eviction closes the host and drops the in-memory entry; `state`, `outputs`, `displays` and errors are already saved and a later read rebuilds the runtime from them. Paused, detached, stopping, saving or active runtimes are never evicted.
19. Script notifications are coalesced: the first `state`/`values` change in a turn is sent at once (so acknowledged data survives a long synchronous block), later ones replace each other and only the last is sent on a microtask. `latest`, versions and dependency invalidation still change synchronously, and flush points precede completion, Pause and Stop. Compiled Script bodies are cached by text (LRU, 100 entries and 8 MB) because the function captures no state.
20. A failed runtime write keeps `dirty` set and reports `storage_error`; a later save retries with the current data. The server replays a `.transaction.json` once at startup; an unreadable record is renamed to `.invalid` and the stored files, which are the source of truth, are served normally.
